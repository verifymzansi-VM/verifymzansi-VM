## Blockers

### B1. Confirmed: deterministic browser audit environment cannot boot without a local Supabase instance
- Journey: all browser-based auth, navigation, posting, billing, and verification flows
- Expected behavior: the Playwright harness should boot a deterministic app instance and allow browser evidence to be regenerated without extra local infrastructure.
- Actual behavior risk: the harness injects `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321`; server-rendered pages then attempt live Supabase fetches and fail before flows can be exercised.
- Likely failure points:
  - `scripts/start-playwright-server.cjs:9`
  - `scripts/start-playwright-server.cjs:12`
- public SSR pages that call `createClient()` during render, for example `src/app/(marketplace)/mzansi-business/page.tsx`
- How to reproduce:
  1. Run `pnpm exec playwright test e2e/auth-qa-audit.spec.ts e2e/critical-flows.spec.ts --project=chromium`.
  2. Observe repeated startup failures with `ECONNREFUSED 127.0.0.1:54321`.
  3. Browser evidence is not regenerated because the app never becomes stable.
- Exact fix recommendation:
  1. Stop pointing the Playwright harness at `127.0.0.1:54321` unless the harness also starts local Supabase.
  2. Prefer a dedicated seeded test Supabase project or a mocked server client for SSR data fetches in `PLAYWRIGHT_TEST_MODE`.
  3. Add a harness preflight that fails fast with a clear message if the configured Supabase endpoint is unreachable.
- Evidence source:
  - `scripts/start-playwright-server.cjs:9`
  - `scripts/start-playwright-server.cjs:12`
  - Playwright run on 2026-03-07 timed out with repeated `ECONNREFUSED 127.0.0.1:54321`

### B2. Confirmed: admin moderation queue exposes business and promotion items that the decision API cannot process
- Journey: staff moderation of seller content
- Expected behavior: anything shown in the admin moderation queue should be approvable or rejectable from the same queue.
- Actual behavior risk: the page loads pending `Mzansi Business` and `Promotions & Events` items, but the decision route only maps legacy market/business-ads/mall-shop areas. Approve/reject on business or promotion items will fail with `Invalid area`.
- Likely failure points:
  - `src/app/admin/moderation/page.tsx:26`
  - `src/app/admin/moderation/page.tsx:59`
  - `src/app/admin/moderation/page.tsx:66`
  - `src/app/admin/moderation/moderation-queue-client.tsx:87`
  - `src/app/api/admin/content/decide/route.ts:59`
- How to reproduce:
  1. Create a pending business or promotion.
  2. Open `/admin/moderation`.
  3. Click `Approve` or `Reject` on that item.
  4. The client posts the item `area`, and the route returns `400 Invalid area`.
- Exact fix recommendation:
  1. Expand `tableMap` in `/api/admin/content/decide` to support `MZANSI_BUSINESS` and `PROMOTIONS_EVENTS`.
  2. Update seller notification logic in that route to resolve owners and destination dashboards for businesses and promotions.
  3. Add route tests for each supported moderation area before reusing the queue for them.
- Evidence source:
  - `src/app/admin/moderation/page.tsx:26`
  - `src/app/admin/moderation/page.tsx:59`
  - `src/app/admin/moderation/page.tsx:66`
  - `src/app/admin/moderation/moderation-queue-client.tsx:87`
  - `src/app/api/admin/content/decide/route.ts:59`
  - No automated coverage exists for `/api/admin/content/decide`

## High

### H1. Confirmed: promotion enquiry dialog posts the wrong request shape and cannot create a contact event
- Journey: public buyer sends an enquiry from a promotion detail page
- Expected behavior: `Send Enquiry` on a promotion should create a contact event and optional lead for the promotion owner, or route through a promotion-specific contact API.
- Actual behavior risk: the promotion page posts `promotionId`, but the API schema only accepts `listingId`. The request fails validation before any seller lookup, lead creation, notification, or audit can happen.
- Likely failure points:
  - `src/app/promotion/[id]/promotion-contact-actions.tsx:27`
  - `src/app/promotion/[id]/promotion-contact-actions.tsx:77`
  - `src/lib/validations/contact.ts:5`
  - `src/app/api/contact/route.ts`
- How to reproduce:
  1. Open any live `/promotion/{id}` page.
  2. Open `Send Enquiry`.
  3. Complete the message and CAPTCHA.
  4. Submit and inspect the API response.
  5. The backend rejects the payload because `listingId` is missing.
- Exact fix recommendation:
  1. Decide whether `/api/contact` should support promotions or whether promotions need a separate contact route.
  2. Align the client and schema on a single canonical payload shape.
  3. Add an automated route test and a component test for promotion enquiries.
- Evidence source:
  - `src/app/promotion/[id]/promotion-contact-actions.tsx:27`
  - `src/app/promotion/[id]/promotion-contact-actions.tsx:77`
  - `src/lib/validations/contact.ts:5`

## Medium

### M1. Confirmed: DSAR success screen shows a fabricated reference instead of the server-issued case reference
- Journey: public DSAR submission
- Expected behavior: after a DSAR submission, the UI should display the exact reference returned by the API so support and privacy staff can reconcile the case.
- Actual behavior risk: the API returns `requestId` and `reference`, but the page ignores them and renders `DSAR-{Date.now()}`. Users can quote a reference that does not exist in the database.
- Likely failure points:
  - `src/app/dsar/page.tsx:137`
  - `src/app/api/dsar/submit/route.ts:112`
- How to reproduce:
  1. Submit the DSAR form successfully.
  2. Compare the success-card reference with the API response payload.
  3. The UI value is time-based, not the persisted server reference.
- Exact fix recommendation:
  1. Store the API `reference` and `requestId` in component state.
  2. Render the server-issued `reference` in the success state.
  3. Optionally expose `requestId` in a copyable support-details section for staff use.
- Evidence source:
  - `src/app/dsar/page.tsx:137`
  - `src/app/api/dsar/submit/route.ts:112`

### M2. Confirmed: DSAR approval writes an in-progress status but logs the case as completed
- Journey: admin DSAR processing
- Expected behavior: audit logs should match the state transition being applied to the case.
- Actual behavior risk: approving a DSAR sets `status = in_progress`, but the audit action is `dsar_completed`. Compliance and audit history can show work as completed before the case is actually completed.
- Likely failure points:
  - `src/app/api/admin/dsar/decide/route.ts`
  - `src/app/api/admin/dsar/decide/route.ts:77`
- How to reproduce:
  1. Approve a submitted DSAR in `/admin/dsar`.
  2. Inspect the updated case row and the emitted audit action.
  3. The row becomes `in_progress`, but the audit event is `dsar_completed`.
- Exact fix recommendation:
  1. Introduce a distinct audit action for the approval-to-processing transition, for example `dsar_started`.
  2. Reserve `dsar_completed` for the later step where the case is actually fulfilled and closed.
  3. Backfill or normalize any downstream reporting that assumes `dsar_completed` means closure.
- Evidence source:
  - `src/app/api/admin/dsar/decide/route.ts:77`

### M3. Confirmed: notification badge can undercount unread items
- Journey: authenticated dashboard/header notifications
- Expected behavior: the bell badge should reflect the API unread count, even when more notifications exist than the first page of hydrated rows.
- Actual behavior risk: the component fetches `/api/notifications?limit=25`, ignores the API `unreadCount`, and recomputes unread count only from the stored slice. Users with more than 25 unread notifications can see a lower count than reality.
- Likely failure points:
  - `src/components/notification-bell.tsx:42`
  - `src/app/api/notifications/route.ts:42`
  - `src/app/api/notifications/route.ts:50`
  - `src/stores/notification-store.ts:53`
  - `src/stores/notification-store.ts:62`
- How to reproduce:
  1. Seed more than 25 unread notifications for one user.
  2. Open the bell dropdown.
  3. Compare the badge count to the API `unreadCount`.
  4. The badge reflects only the hydrated slice.
- Exact fix recommendation:
  1. Hydrate both `notifications` and `unreadCount` from the API payload.
  2. Preserve server unread count separately from the visible list length.
  3. Add a store/component test covering 25+ unread notifications.
- Evidence source:
  - `src/components/notification-bell.tsx:42`
  - `src/app/api/notifications/route.ts:42`

### M4. Inferred Risk: OTP provider failure still consumes hourly send quota and leaves a live challenge behind
- Journey: verification phone step
- Expected behavior: if SMS delivery fails and the user receives a `502`, the send attempt should either be rolled back or clearly excluded from the per-hour quota.
- Actual behavior risk: the route inserts into `otp_challenges` before calling the SMS provider. If SMS delivery fails, the user gets `502 Failed to send OTP`, but the attempt still counts toward `MAX_SENDS_PER_HOUR` and the live challenge remains stored.
- Likely failure points:
  - `src/app/api/otp/send/route.ts:11`
  - `src/app/api/otp/send/route.ts:175`
  - `src/app/api/otp/send/route.ts:232`
- How to reproduce:
  1. Force `sendOtpSms` to fail or misconfigure the SMS provider.
  2. Trigger `/api/otp/send` repeatedly.
  3. Observe `502 Failed to send OTP. Please try again.` responses.
  4. Continue until the route reaches the hourly send cap from failed sends alone.
- Exact fix recommendation:
  1. Mark failed-delivery challenges as cancelled/invalid, or delay challenge creation until the provider accepts the message.
  2. Exclude failed-delivery attempts from the quota query, or track send outcome separately.
  3. Add a route test that asserts quota behavior under repeated SMS-provider failure.
- Evidence source:
  - `src/app/api/otp/send/route.ts:11`
  - `src/app/api/otp/send/route.ts:175`
  - `src/app/api/otp/send/route.ts:232`

- Seller CRUD route coverage is currently healthy for the tested paths:
  - listings
  - businesses
  - promotions
- Billing backend coverage is healthy for:
  - checkout session creation
  - PayFast webhook fulfillment
- KYC backend coverage is healthy for:
  - verification decision route
  - GPS verification route
  - upload/KYC security behaviors covered by existing tests
- Public trust backend coverage is healthy for:
  - contact route contract tests
  - report route contract tests
  - DSAR validation tests

These green tests reduce risk, but they do not override the contract mismatches above because several of those paths currently have no direct automated coverage.

## Coverage Gaps

- No direct automated coverage for `/api/admin/content/decide`, despite it being the write path for the moderation queue.
- No automated component or route test for promotion enquiries.
- No automated end-to-end coverage for promotion report reasons against the live schema.
- No automated assertion that the DSAR success UI renders the server-issued reference.
- No automated coverage for the notification bell when unread notifications exceed the hydrated page size.

## Recommended Fix Order

1. Repair the deterministic browser harness so browser evidence can be regenerated on demand.
2. Fix the admin moderation area map so businesses and promotions can actually be approved or rejected.
3. Align promotion enquiry and promotion reporting contracts with their APIs.
4. Fix DSAR reference and audit-state mismatches.
5. Fix notification count accuracy and OTP failure accounting.
